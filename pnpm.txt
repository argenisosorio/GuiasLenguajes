===========
Instalación
===========

En esta forma de instalación usaremos nvm, que es un administrador de versiones
para node.js, diseñado para ser instalado por el usuario e invocado por shell.

Se recomienda seguir la documentación disponible desde:
https://linuxconfig.org/how-to-install-node-js-on-ubuntu-16-04-xenial-xerus-linux-server
pero para este manual recomendamos los siguientes pasos:

Procedimiento de instalación mediante el script nativo de node **nvm** el cual
permite más control en cuanto a la versión de **node** y **npm** a ser
instalada.

Instalar los prerequisitos del S.O. mediante el siguiente comando:

$ sudo apt install build-essential libssl-dev

Descargar el script de instalación más reciente mediante **curl**, para ello
se requiere ejecutar el comando:

$ sudo curl -o- https://raw.githubusercontent.com/creationix/nvm/{version}/install.sh | bash

Se debe sustituir la número de versión con la más reciente publicada la
cual se puede encontrar [aquí](https://github.com/nvm-sh/nvm/releases), ejemplo:

$ sudo curl -o- https://raw.githubusercontent.com/creationix/nvm/v0.34.0/install.sh | bash

Lo siguiente es configurar el acceso del nuevo script **NVM** con el siguiente
comando:

$ . ~/.profile

Esto permitira acceder al comando nvm desde cualquier ruta, una vez realizada
la configuración, se procederá a verificar el listado de versiones de **node**
disponibles en el repositorio para lo cual se require ejecutar el comando:

$ nvm ls-remote | grep -i lts

Esto debe mostrar un listado de versiones de node que correspondan
a las versiones **LTS**, ejemplo:

v10.15.3   (LTS: Dubnium)
v10.16.0   (LTS: Dubnium)
v10.16.1   (LTS: Dubnium)
v10.16.2   (LTS: Dubnium)
v10.16.3   (Latest LTS: Dubnium)

Ahora procedemos a la instalación de la versión de node más actualizada para lo
cual se ejecutará el comando:

$ nvm install 10.16.3

Una vez instalado NodeJS comprobamos la correcta instalación con el siguiente
comando:

$ node -v

Los comandos anteriores nos instalaran NodeJS y también npm, por lo cual
comprobamos su correcta instalación con el siguiente comando:

$ npm -v

Usar una versión específica de node
===================================

Si se tienen varias versiones de node insaladas se pude especificar que se use
una en esa sesión:

$ nvm use 10.16.3

Hacer que una versión de node sea la configurada por defecto
============================================================

$ nvm alias default 10.16.3

Ya que tenemos instalado node y npm podemos instalar pnpm.

Este comando intenta instalar globalmente en tu sistema la versión más reciente
dentro de la línea v11 del gestor de paquetes pnpm usando npm.

La sintaxis @latest-11 es un dist-tag (etiqueta de distribución) de npm que
apunta a la versión estable más reciente dentro de esa rama principal
específica.

$ npm install -g pnpm@latest-11

¿Cómo instalar una versión específica de pnpm?

Dependiendo del método que prefieras usar, tienes las siguientes opciones:

Opción 1: Usando npm (Recomendado si ya tienes Node.js)

Para instalar una versión exacta, sustituye la etiqueta por el número de versión
específico:

$ npm install -g pnpm@9.15.0

Si solo quieres instalar la versión más reciente de todas (la última lanzada):

$ npm install -g pnpm@latest

Opción 2: Usando Corepack (Incluido en Node.js)

Node.js incluye de forma nativa corepack, que permite gestionar versiones de
pnpm sin necesidad de instalarlo globalmente vía npm.

1. Activa Corepack:

$ corepack enable

2. Prepara e instala la versión específica que necesitas:

$ corepack prepare pnpm@9.15.0 --activate

Opción 3: Actualizar una versión existente con el propio pnpm

Si ya tienes pnpm instalado y quieres cambiar o actualizar a una versión
específica:

$ pnpm self-update 9.15.0

===========
npm vs pnpm
===========

Si alguna vez has sentido que tu carpeta node_modules pesa más que tu propia
alma, entender la diferencia entre npm y pnpm te va a cambiar la vida. Ambos son
gestores de paquetes para Node.js, pero funcionan bajo filosofías muy distintas.

1. La diferencia fundamental: El almacenamiento

La mayor diferencia radica en cómo guardan los paquetes en tu disco duro.

-npm (Node Package Manager): Es el estándar por defecto. Si tienes 10 proyectos
que usan lodash, npm descargará y guardará 10 copias de lodash, una en cada
carpeta node_modules. Es ineficiente con el espacio.

pnpm (Performant npm): Utiliza un almacén de contenido direccionable
(Content-addressable store). Si 10 proyectos usan lodash, pnpm solo guarda una
copia en una carpeta global de tu disco y crea "enlaces" (hard links) hacia
ella.

Resultado: Ahorras gigabytes de espacio y las instalaciones son ridículamente
rápidas.

2. Velocidad y Rendimiento

En la mayoría de las comparativas, pnpm gana por goleada.

+----------------------+-------------------------------+----------------------------------+
| Característica       | npm                           | pnpm                             |
+----------------------+-------------------------------+----------------------------------+
| Instalación inicial  | Lenta (descarga todo de nuevo)| Muy rápida (usa el caché global) |
+----------------------+-------------------------------+----------------------------------+
| Uso de disco         | Muy alto                      | Muy bajo (enlaces simbólicos)    |
+----------------------+-------------------------------+----------------------------------+
| Seguridad            | Buena                         | Excelente (evita dep. fantasma)  |
+----------------------+-------------------------------+----------------------------------+
| Madurez              | El estándar de la industria   | Cada vez más usado               |
+----------------------+-------------------------------+----------------------------------+

3. El problema de las "Dependencias Fantasma"

npm utiliza una estructura plana (flattened). Esto significa que si instalas el
paquete A, y este depende del paquete B, npm pone a ambos en la raíz de
node_modules. Esto te permite usar el paquete B en tu código aunque no lo hayas
instalado tú directamente.

pnpm no permite esto. Utiliza enlaces simbólicos para crear una estructura
estricta. Solo puedes importar lo que declaraste explícitamente en tu
package.json. Esto evita errores misteriosos en producción.

4. Comandos básicos

La buena noticia es que la curva de aprendizaje es casi nula porque los comandos
son prácticamente idénticos:

Instalar dependencias:

-npm: npm install

-pnpm: pnpm install

Añadir un paquete:

-npm: npm install express

-pnpm: pnpm add express

Ejecutar un script:

-npm: npm run dev

-pnpm: pnpm dev (ni siquiera necesitas el "run")

¿Cuál deberías elegir?

Usa npm si: Eres principiante, quieres evitar configurar herramientas
adicionales o trabajas en un equipo que no quiere cambiar su flujo de trabajo
actual.

Usa pnpm si: Tienes poco espacio en disco, trabajas en monorepos (donde pnpm
brilla especialmente) o simplemente odias esperar minutos a que termine un
install.

Ejemplo práctico: Un "Hola Mundo" con el paquete confeti
========================================================

Para notar la ventaja real de pnpm, lo ideal es ver cómo maneja el espacio en
disco comparado con npm. El "truco" está en que pnpm no duplica archivos; si dos
proyectos usan la misma librería, solo ocupa espacio una vez.

Aquí tienes un ejercicio práctico para que lo compruebes tú mismo:

Paso 1: Instalación (si no lo tienes)

Si tienes Node.js instalado, puedes activar pnpm rápidamente:

$ corepack enable

O vía npm:

$ npm install -g pnpm

Verificar la versión instalada:

$ pnpm -v

Paso 2: Crear el Proyecto A

Para notar la ventaja real de pnpm, vamos a usar canvas-confetti, un paquete que
añade una animación festiva a tu index.html.

$ mkdir proyecto-confeti-a && cd proyecto-confeti-a

$ pnpm init

$ pnpm add canvas-confetti

El comando anterior va a fallar con un error como este:

Invalid package manager specification in package.json (pnpm@^11.1.1); expected a
semver version

El error ocurre porque la especificación packageManager (y en este caso, la
extensión devEngines) no acepta rangos de versiones como ^11.1.1. Este campo
requiere una versión exacta (un string fijo) para asegurar que todos los
desarrolladores usen la misma versión del gestor de paquetes.

Para solucionarlo, debes editar tu package.json y eliminar el símbolo ^.

Modifica la sección de devEngines (o packageManager si la usaras directamente)
para que quede así:

{
  "name": "proyecto-confeti-a",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC",
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "11.1.1",
      "onFail": "download"
    }
  },
  "type": "module"
}

Ejecuta de nuevo este comando para que se instale el paquete:

$ pnpm add canvas-confetti

Esto habrá creado la carpeta node_modules y el archivo pnpm-lock.yaml

Ahora, crea un archivo index.html básico:

<!DOCTYPE html>
<html>
<body>
  <h1>¡Hola Mundo con pnpm!</h1>
  <script type="module">
    import confetti from './node_modules/canvas-confetti/dist/confetti.module.mjs';
    confetti();
  </script>
</body>
</html>

En este momento, pnpm descargó el paquete a una carpeta global y creó un enlace
en tu proyecto.

Paso 3: Probar el index.html

Usaremos un servidor local, para que el navegador trate tu proyecto como un
sitio web real, necesitas servirlo a través de un servidor local. Como ya tienes
pnpm y Node.js, la forma más rápida es usar un paquete llamado serve o
live-server.

Ejecuta este comando en tu terminal (dentro de proyecto-a):

$ pnpm dlx serve .

Al abrir http://localhost:3000/ deberías ver el Hola mundo y una animación de
confeti.

Imagina que quieres otro proyecto igual, el B.

¿Qué acaba de pasar?
====================

-Es instantáneo: La instalación en el segundo proyecto toma milisegundos porque
el código ya está en el almacén global de tu disco.

-No ocupa espacio extra: Aunque veas la carpeta node_modules, no hay una segunda
copia física del paquete. Ambos proyectos están "viendo" el mismo archivo
centralizado.

¿Cómo verificar la ventaja de espacio? Puedes ver dónde guarda pnpm los archivos
realmente con:

$ pnpm store path

Tus carpetas node_modules son técnicamente "espejos" (enlaces simbólicos) que
apuntan a esa ruta única.

Revisión de la estructura:

$ tree

├── index.html
├── node_modules
│   └── canvas-confetti -> .pnpm/canvas-confetti@1.9.4/node_modules/canvas-confetti
├── package.json
└── pnpm-lock.yaml

Esa salida del comando tree es la prueba perfecta de cómo funciona pnpm por
debajo. Fíjate en la flecha (->):

canvas-confetti -> .pnpm/canvas-confetti@1.9.4/node_modules/canvas-confetti

Esto confirma que canvas-confetti en tu carpeta node_modules no es una carpeta
real con archivos dentro, sino un enlace simbólico (symlink).

Resumen del beneficio:
======================

-Velocidad: El Proyecto B se configuró sin descargar nada de internet.

-Espacio: Si haces 50 pequeños experimentos con confeti, solo ocupas el espacio
de 1.

-Seguridad: Tienes la certeza de que el paquete es idéntico en todos tus
proyectos.

========================
Errores con node_modules
========================

Antes se usaba el viejo "borrón y cuenta nueva" de npm borrando la carpeta
node_modules. Sin embargo, la gran ventaja de haber migrado el entorno a pnpm es
que maneja las dependencias mediante un almacén global indexado
(el virtual store) y enlaces simbólicos (symlinks). Esto significa que los
problemas de corrupción de paquetes son muchísimo menos comunes, pero cuando
ocurren, la forma de solucionarlos cambia un poco.

1. La alternativa directa al clásico rm -rf node_modules

Si sospechas que los enlaces simbólicos de tu proyecto local se rompieron o
quedaron corruptos, puedes recrearlos en un segundo sin tener que volver a
descargar nada de internet.

Ejecuta en la raíz de tu proyecto:

$ pnpm store prune

$ pnpm install --force

pnpm store prune: Elimina del almacén global todos los paquetes huérfanos que ya
no se usan en ningún proyecto, liberando espacio.

--force: Le dice a pnpm que reconstruya la carpeta node_modules desde cero,
verificando y reemplazando todos los archivos modificados o corruptos utilizando
el caché global. ¡Es increíblemente rápido comparado con npm!

2. El reinicio "Hard" (El equivalente exacto a tu vieja costumbre)

Si quieres replicar exactamente el comportamiento de borrar todo y reinstalar
(por ejemplo, si cambiaste drásticamente de rama o sospechas del archivo de
bloqueo), puedes limpiar el directorio local y reinstalar de forma limpia:

En Linux/Debian:

$ rm -rf node_modules pnpm-lock.yaml && pnpm install

Nota: Al borrar el pnpm-lock.yaml, forzarás a pnpm a recalcular el árbol de
dependencias completo en su versión compatible más reciente según tu
package.json.

3. Verificar la integridad del almacén global

A veces, el problema no está en tu proyecto, sino en que algún archivo dentro
del almacén global de pnpm se corrompió (por ejemplo, si un proceso se
interrumpió abruptamente).

Para verificar si todos los paquetes del caché coinciden exactamente con sus
sumas de verificación (checksums) originales, usa:

$ pnpm store status

Si el comando detecta que algún paquete fue modificado externamente o está
corrupto, te avisará para que puedas correr un pnpm install --force y repararlo.

================================
Comandos run dentro del proyecto
================================

¿En mi proyecto de nuxt con pnpm en que archivo puedo ver los comandos como pnpm
run dev configurados o el lint?

En un proyecto de Nuxt (o en cualquier proyecto de JavaScript/TypeScript Node.js
que use pnpm, npm o yarn), todos estos comandos están configurados en el
archivo package.json, específicamente dentro de la sección "scripts".

Este archivo se encuentra siempre en la raíz de tu proyecto.

¿Cómo se ve dentro del archivo?

Si abres el archivo package.json, verás una estructura muy similar a esta:

{
  "name": "tu-proyecto-nuxt",
  "private": true,
  "type": "module",
  "scripts": {
    "build": "nuxt build",
    "dev": "nuxt dev",
    "generate": "nuxt generate",
    "preview": "nuxt preview",
    "postinstall": "nuxt prepare",
    "lint": "eslint ."
  },
  "dependencies": {
    "nuxt": "^4.0.0"
  },
  "devDependencies": {
    "eslint": "^9.0.0"
  }
}

¿Qué significa cada parte en "scripts"?

"dev": "nuxt dev": Es el comando que se ejecuta cuando escribes pnpm run dev (o
simplemente pnpm dev). Levanta el servidor de desarrollo local de Nuxt.

"lint": "eslint ." (o similar): Es el comando que se ejecuta con pnpm run lint.
Se encarga de analizar tu código en busca de errores de estilo o de sintaxis
usando herramientas como ESLint.

"build": "nuxt build": Compila tu aplicación de Nuxt para producción.

Un par de trucos útiles con pnpm:

A diferencia de npm, con pnpm tienes un par de atajos muy cómodos en la terminal:

1. No necesitas escribir run para la mayoría de comandos: En lugar de pnpm run
dev o pnpm run lint, puedes escribir simplemente:

$ pnpm dev

$ pnpm lint

2. Ver todos los comandos disponibles sin abrir el archivo:

Si estás en la terminal y quieres ver rápidamente qué comandos tienes
configurados sin tener que abrir el package.json, puedes ejecutar:

$ pnpm run

Esto te mostrará una lista interactiva en la terminal con todos los scripts que
puedes lanzar.

=========
pnpm test
=========

Es un comando que ejecuta los tests (pruebas automatizadas) de tu proyecto de
JavaScript o TypeScript utilizando pnpm, un gestor de paquetes alternativo a
npm o yarn conocido por ser extremadamente rápido y eficiente con el espacio en
disco.

En realidad, pnpm test es solo un alias o un acceso directo. Lo que hace por
detrás es buscar la instrucción test dentro del archivo package.json de tu
proyecto y ejecutar la herramienta de pruebas que tengas configurada ahí (como
Jest, Vitest, Mocha, Playwright, etc.).

¿Cómo funciona y cómo se usa?

1. La configuración básica (package.json)

Para poder usar pnpm test, tu proyecto debe tener definida una secuencia de
comandos (script) llamada "test" en su archivo package.json.

Por ejemplo:

{
  "name": "mi-proyecto",
  "scripts": {
    "test": "vitest"
  }
}

2. Formas comunes de ejecutarlo

Ejecutar todas las pruebas: Abre la terminal en la raíz de tu proyecto y escribe:

$ pnpm test

O su versión corta:

$ pnpm t

Ejecutar un archivo de prueba específico: Puedes pasar el nombre o la ruta del
archivo directamente:

$ pnpm test src/auth.test.ts

Pasar argumentos adicionales a tu framework de tests: Si quieres pasar opciones
especiales (por ejemplo, para ver la cobertura de código o ejecutar en modo
observación/watch), simplemente añade la bandera al final:

Generar reporte de cobertura (si usas Jest/Vitest)

$ pnpm test --coverage

Ejemplo real sencillo
=====================

Vamos a crear un ejemplo súper sencillo desde cero en 5 pasos para que veas
exactamente cómo funciona sin complicarte con librerías pesadas.

1.Crea una carpeta e inicializa el proyecto: Abre tu terminal y ejecuta los
siguientes comandos para crear un directorio nuevo e inicializar el archivo
package.json:

$ mkdir ejemplo-pnpm-test

$ cd ejemplo-pnpm-test

$ pnpm init

2. Instala la herramienta de pruebas (Vitest): Usaremos Vitest por ser
extremadamente rápido y no requerir ninguna configuración extra para funcionar:

$ pnpm add -D vitest

3. Crea la función y su archivo de prueba: Crea dos archivos en la raíz de la
carpeta: math.js (El código de tu aplicación):

export function sumar(a, b) {
  return a + b;
}

math.test.js (El archivo con la prueba):

import { expect, test } from 'vitest';
import { sumar } from './math.js';

test('suma 2 + 3 y devuelve 5', () => {
  expect(sumar(2, 3)).toBe(5);
});

4. Configura el script en package.json: Abre el archivo package.json y añade la
instrucción "test": "vitest run" dentro de la sección "scripts". Debe verse
parecido a esto:

{
  "name": "ejemplo-pnpm-test",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "test": "vitest run"
  },
  "devDependencies": {
    "vitest": "^3.0.0"
  }
}

Nota: La propiedad "type": "module" es importante para poder usar import/export
en JavaScript.

5. ¡Ejecuta pnpm test!: En tu terminal, ejecuta:

$ pnpm test

¿Qué verás en la terminal? Si todo salió bien, Vitest ejecutará la función
sumar(2, 3), comprobará si da 5 y verás una salida con éxito en verde parecida a
esta:
✓ math.test.js (1)
  ✓ suma 2 + 3 y devuelve 5

Test Files  1 passed (1)
  Tests  1 passed (1)

Prueba cambiar la respuesta para ver un fallo: Si cambias el 5 en math.test.js
por un 10 y vuelves a ejecutar pnpm test, verás cómo la terminal resalta en rojo
dónde ocurrió el error.
