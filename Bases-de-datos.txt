================================================================================
MÓDULO B1: FUNDAMENTOS TEÓRICOS DE LOS DATOS
================================================================================

----------------------------------------------------------
1. Diferencia entre Dato, Información y Base de Datos
----------------------------------------------------------

- Dato: Es la unidad mínima de hecho bruto, sin contexto ni significado por sí
  mismo. Ejemplo: "35", "1990-05-12", "azul". Un dato, por sí solo, no
  responde nada todavía.

- Información: Es el dato procesado, interpretado y dotado de contexto, de modo
  que adquiere significado para quien lo usa. Ejemplo: "El cliente de id 35
  nació el 12/05/1990". La información es dato + contexto + relevancia.

- Base de Datos (BD): Es una colección organizada y persistente de datos
  relacionados entre sí, estructurada de forma que permita almacenarla, operarla
  y consultarla de manera eficiente. No es un simple "montón de archivos": tiene
  un esquema, reglas de integridad y mecanismos de acceso.

  Ejemplo del flujo completo:
  - Dato: "Pedro", "lopez@mail.com", "2024-01-10".
  - Información: "El usuario Pedro López se registró el 10/01/2024".
  - Base de datos: la tabla usuarios (o similar) que guarda cientos de
    registros de ese tipo, con reglas (email único, fecha obligatoria) e
    índices para localizarlos con rapidez.

----------------------------------------------------------
2. ¿Qué es un SGBD / DBMS?
----------------------------------------------------------

- SGBD (en español) / DBMS (Database Management System, en inglés) es un
  software cuyo propósito es gestionar, almacenar, modificar, recuperar y
  proteger los datos de una base de datos, de forma segura y concurrente.

Funciones principales de un SGBD:
  - Definir y administrar el esquema (estructura) de los datos.
  - Proporcionar un lenguaje de acceso (SQL) y optimizarlo (planificador de
    consultas).
  - Controlar el acceso concurrente de muchos usuarios (transacciones ACID).
  - Garantizar la integridad y la seguridad de los datos.
  - Realizar copias de seguridad y recuperación ante fallos.

Ejemplos de SGBD: PostgreSQL, MySQL, MariaDB, Microsoft SQL Server, Oracle,
SQLite.

SGBD vs archivo de texto vs hoja de cálculo:
  - Archivo de texto (.txt, .csv): Almacena datos planos sin estructura ni
    reglas. Cada programa debe parsearlos; no hay validación, concurrencia,
    transacciones ni consultas optimizadas. Si dos procesos escriben a la vez,
    el archivo se corrompe.
  - Hoja de cálculo (Excel, Sheets): Organiza datos en celdas y permite
    fórmulas, pero es un documento, no un sistema: no maneja concurrencia
    multiusuario, apenas aplica restricciones de integridad, no tiene SQL y
    escala mal.
  - SGBD: Base de datos + motor que garantiza integridad, concurrencia,
    seguridad, transacciones, respaldo y consultas eficientes (con índices y
    optimizador). Resumen: la diferencia entre "guardar datos" y "gestionar
    datos".


================================================================================
MÓDULO B2: MODELADO DE DATOS
================================================================================

El modelado de datos es la actividad previa a crear tablas: se dibuja y define
"qué datos existen y cómo se relacionan" ANTES de escribir ningún CREATE TABLE.

----------------------------------------------------------
1. Modelo Entidad-Relación (MER)
----------------------------------------------------------

Es un modelo conceptual, independiente del SGBD, que describe el mundo real en
términos de entidades, atributos y relaciones.

- Entidad: Objeto o concepto del mundo real distinguible de los demás. Puede
  ser concreta (CLIENTE, PRODUCTO) o abstracta (PEDIDO, MATRÍCULA). En el DER
  se representa con un rectángulo.

- Atributo: Propiedad o característica de una entidad. En el DER se representa
  con un óvalo unido a su entidad.
  * Simples (o atómicos): No se pueden dividir. Ejemplo: edad.
  * Compuestos: Se pueden descomponer en partes más pequeñas. Ejemplo:
    dirección = calle + número + ciudad; nombre_completo = nombre + apellidos.
  * Multivaluados: Pueden tener varios valores a la vez para una misma entidad.
    Ejemplo: un EMPLEADO puede tener varios teléfonos. En el DER se representan
    con un óvalo doble.

- Relación: Asociación entre dos o más entidades. En el DER se representa con
  un rombo. Tiene un nombre y una cardinalidad.

Tipos de relaciones (por cardinalidad):
  - 1 a 1 (1:1): Un registro de la tabla A solo se relaciona con un registro de
    la tabla B y viceversa. Ejemplos: Países-Banderas (cada país tiene una
    única bandera oficial), Matrículas-Coche.
  - 1 a varios (1:N): Un registro de A se relaciona con varios de B, pero cada
    registro de B se relaciona con uno solo de A. Es el tipo más habitual.
    Ejemplos: domicilios con las personas que viven en él, empresa con sus
    trabajadores, proveedor con los productos que sirve.
  - Varios a varios (N:M): Varios registros de A se relacionan con varios de B y
    viceversa. Se implementa con una tabla intermedia (tabla puente). Ejemplo
    clásico: actores y películas (un actor trabaja en muchas películas y cada
    película tiene varios actores).

La cardinalidad mínima (opcionalidad) también importa: "cada pedido DEBE tener
un cliente" (mínima 1) frente a "un cliente PUEDE tener pedidos" (mínima 0).

Otros ejemplos cotidianos:

1 a 1 (1:1)
===========

-Un registro de A corresponde solo a un registro de B, y viceversa.

-Persona y Número de Pasaporte: Una persona tiene un único pasaporte oficial, y
ese número de pasaporte le pertenece solo a esa persona.

-Usuario y Cuenta de Configuración: Un usuario de una app tiene un solo panel de
ajustes, y ese panel de ajustes pertenece a un único usuario.

1 a Muchos (1:N)
================

-Un registro de A se relaciona con varios de B, pero cada registro de B
pertenece solo a un A.

-Cliente y Facturas: Un cliente puede hacer muchas compras y tener varias
facturas, pero cada factura pertenece a un solo cliente.

-Autor y Libros: Un autor escribe muchos libros, pero un libro específico (en
su edición original) es de un solo autor principal.

Muchos a Muchos (N:M)
=====================

-Varios registros de A se relacionan con varios de B, y viceversa.

-Estudiantes y Cursos: Un estudiante se inscribe en varias materias, y cada
materia tiene inscritos a muchos estudiantes.

-Canciones y Listas de Reproducción (Playlists): Una canción puede estar en
muchas playlists diferentes, y cada playlist tiene muchas canciones.

----------------------------------------------------------
2. Modelo Relacional
----------------------------------------------------------

Es la traducción del MER a una estructura entendible por los SGBD
relacionales: tablas, filas y columnas, con tipos de datos y claves.

Términos formales (y su nombre coloquial):
  - Dominio: Conjunto de valores válidos que puede tomar un atributo (el "tipo"
    de datos con sus restricciones). Ejemplo: dominio "edad" = enteros entre 0
    y 120.
  - Tupla: Cada fila de la tabla (cada registro). Las filas son "tuplas" de la
    relación.
  - Atributo: Cada columna de la tabla (cada campo).
  - Grado (o aridad): Número de columnas (atributos) de una relación.
  - Cardinalidad (de la relación como conjunto): Número de filas (tuplas).

Ejemplo: la tabla usuarios tiene grado 4 (id, email, nombre, fecha) y su
cardinalidad crece con cada INSERT.

Reglas para que una tabla sea considerada una relación válida:
  - Cada tabla debe tener un nombre único.
  - No pueden existir dos filas idénticas (no se permiten duplicados).
  - Todos los datos de una columna deben ser del mismo tipo (mismo dominio).

----------------------------------------------------------
3. Diferencia entre DER y Esquema de Base de Datos
----------------------------------------------------------

- Diagrama Entidad-Relación (DER): Es el diagrama del modelo conceptual. Usa
  símbolos (rectángulos, óvalos, rombos, líneas) y describe el "qué" del
  problema de negocio. No contiene comandos SQL ni tipos de datos definitivos.

- Esquema de la Base de Datos (esquema relacional): Es la descripción lógica y
  física de las tablas implementadas en un SGBD concreto: CREATE TABLE, tipos
  de datos determinados, claves primarias/foráneas y restricciones. Es el
  "cómo" se guarda.

Resumen: primero se dibuja el MER/DER (diseño conceptual) y después se crea el
esquema relacional (diseño lógico/físico). El MER es el plano; el esquema es
la construcción.

Jerarquía de diseño:
  Modelo Conceptual (MER/DER)  ->  Modelo Lógico (esquema relacional)
  ->  Modelo Físico (índices, particiones, almacenamiento)

================================================================================
MÓDULO B3: FUNDAMENTOS DEL LENGUAJE SQL (SUB-LENGUAJES)
================================================================================

SQL (por sus siglas en inglés Structured Query Language; en español lenguaje de
consulta estructurada) es un lenguaje de dominio específico utilizado en
programación, diseñado para administrar y recuperar información de sistemas de
gestión de bases de datos relacionales. Una de sus principales características
es el manejo del álgebra y el cálculo relacional para efectuar consultas
sencillas y realizar cambios en la base de datos. Aunque normalmente se lo
describe como un lenguaje declarativo, también incluye elementos
procedimentales.

El alcance de SQL incluye la inserción de datos, consultas, actualizaciones y
borrado, la creación y modificación de esquemas y el control de acceso a los
datos. Se organiza en cuatro sub-lenguajes según su función:

----------------------------------------------------------
1. DDL - Data Definition Language (lenguaje de definición de datos)
----------------------------------------------------------
Define la estructura (el esquema), no los datos.

  - CREATE: Crea bases de datos, tablas, vistas, índices.
        CREATE TABLE usuarios (id SERIAL PRIMARY KEY, email VARCHAR(100));
  - ALTER: Modifica una estructura existente.
        ALTER TABLE usuarios ADD COLUMN telefono VARCHAR(20);
  - DROP: Elimina por completo una estructura (con su contenido).
        DROP TABLE usuarios;
  - TRUNCATE: Vacía todos los datos de una tabla conservando su estructura.
        TRUNCATE TABLE usuarios;
    Diferencia clave: TRUNCATE elimina todas las filas sin recorrerlas (no
    dispara triggers y no se puede deshacer fácilmente), a diferencia de
    DELETE, que es DML, dispara triggers y puede revertirse dentro de una
    transacción.

----------------------------------------------------------
2. DML - Data Manipulation Language (lenguaje de manipulación de datos)
----------------------------------------------------------
Manipula el contenido (los datos dentro de las tablas).

  - SELECT: Consulta / lectura de datos.
        SELECT * FROM usuarios WHERE id = 1;
  - INSERT: Inserta nuevas filas.
        INSERT INTO usuarios (email) VALUES ('a@b.com');
  - UPDATE: Modifica filas existentes.
        UPDATE usuarios SET email = 'nuevo@b.com' WHERE id = 1;
  - DELETE: Elimina filas (respeta la integridad referencial y dispara
    triggers).
        DELETE FROM usuarios WHERE id = 1;

----------------------------------------------------------
3. DCL - Data Control Language (lenguaje de control de datos)
----------------------------------------------------------
Administra los permisos de los usuarios sobre los objetos.

  - GRANT: Otorga privilegios.
        GRANT SELECT, INSERT ON usuarios TO aplicacion;
  - REVOKE: Retira privilegios.
        REVOKE UPDATE ON usuarios FROM aplicacion;

----------------------------------------------------------
4. TCL - Transaction Control Language (lenguaje de control de transacciones)
----------------------------------------------------------
Gestiona las transacciones (unidades de trabajo atómicas).

  - COMMIT: Confirma de forma definitiva los cambios de la transacción.
  - ROLLBACK: Deshace los cambios de la transacción (vuelve al estado previo).
  - SAVEPOINT: Punto de guardado intermedio para poder hacer ROLLBACK parcial.

        BEGIN;
        SAVEPOINT antes_del_error;
        INSERT ...;                       -- si algo falla a partir de aquí:
        ROLLBACK TO antes_del_error;      -- deshace solo desde el savepoint
        COMMIT;                           -- confirma lo demás


================================================================================
MÓDULO B4: TIPOS DE DATOS ESTÁNDAR
================================================================================

Elegir el tipo correcto de cada columna define el dominio de valores válidos y
afecta el espacio en disco, la velocidad y la corrección de las consultas.

----------------------------------------------------------
1. Cadenas (strings)
----------------------------------------------------------
  - CHAR(n): Longitud fija, rellena con espacios. Útil cuando el tamaño es
    siempre el mismo (códigos de país, DNI).
  - VARCHAR(n): Longitud variable con un límite máximo n. El más usado para
    textos cortos o medianos (nombres, correos).
  - TEXT: Longitud sin límite práctico (en PostgreSQL). Para párrafos,
    descripciones largas o contenido extenso.

Regla práctica: VARCHAR para valores cortos y acotados; TEXT para contenido
extenso; no abusar de límites arbitrarios innecesarios.

----------------------------------------------------------
2. Números
----------------------------------------------------------
  - INT / integer: Entero de 4 bytes. Rango aproximado de ±2.1 miles de
    millones. El tipo más común para claves primarias (id) normales.
  - BIGINT / biginteger: Entero de 8 bytes. Para números astronómicos: grandes
    identificadores, conteos de visitas de sitios populares o cifras
    financieras globales. Se usa cuando el rango de integer puede desbordarse.
  - DECIMAL(p,s) / NUMERIC(p,s): Números exactos de precisión fija, sin errores
    de redondeo. Indispensable para dinero. Ejemplo: NUMERIC(10,2) = 10 dígitos
    en total, 2 decimales.
  - FLOAT / DOUBLE / REAL: Números de punto flotante (aproximados). Son
    rápidos pero tienen errores de redondeo. Usar para medidas científicas,
    estadísticas; NO para dinero.
  - SERIAL / IDENTITY / AUTO_INCREMENT: Entero auto-incrementado, habitual para
    claves primarias (el nombre varía según el SGBD).

Resumen práctico: id normal -> INT; id o suma astronómica -> BIGINT; dinero ->
NUMERIC/DECIMAL; medidas aproximadas -> FLOAT/DOUBLE.

¿Cuándo usar integer y cuándo biginteger?
  - integer es más eficiente en memoria y almacenamiento; sirve cuando sabes
    que los números no serán muy grandes (la mayoría de identificadores o
    conteos que no superan los dos mil millones).
  - biginteger es para valores extremadamente grandes: sistema que gestiona
    enormes bases de datos o cifras, como el total de visitas de una página
    popular, cifras financieras globales o grandes identificadores.

Ejemplo práctico: si esperas que un id nunca supere los dos mil millones, usa
integer. Si un conteo (transacciones, usuarios) puede llegar a cifras
astronómicas, usa biginteger.

----------------------------------------------------------
3. Fechas y horas
----------------------------------------------------------
  - DATE: solo la fecha (año, mes y día). Ejemplo: 2024-03-15.
  - TIME: solo la hora (sin fecha). Ejemplo: 14:30:00.
  - TIMESTAMP: fecha + hora. Ejemplo: 2024-03-15 14:30:00.
  - TIMESTAMP WITH TIME ZONE (TIMESTAMPTZ en PostgreSQL): fecha + hora más la
    zona horaria. Almacena en UTC y convierte según el huso del cliente.

Regla de oro: para aplicaciones multinacionales o eventos, usar TIMESTAMPTZ (no
TIMESTAMP), porque un TIMESTAMP sin zona es ambiguo.
  - DEFAULT CURRENT_TIMESTAMP es la forma habitual de registrar "fecha de
    creación".

----------------------------------------------------------
4. Booleanos y NULL (la lógica tri-valor en SQL)
----------------------------------------------------------
  - BOOLEAN: TRUE / FALSE. Expresa condiciones del tipo sí/no (activo,
    verificado).
  - NULL: NO es un valor, ni un cero, ni una cadena vacía. Significa "ausencia
    de dato" o "desconocido".

Lógica tri-valor del SQL: toda comparación puede dar TRES resultados: VERDADERO,
FALSO o DESCONOCIDO (NULL).

Consecuencias importantes:
  - NULL = NULL NO es verdadero: es DESCONOCIDO. Para comparar nulos se usa
    IS NULL / IS NOT NULL, nunca "= NULL".
  - En un WHERE, las filas que evalúan a DESCONOCIDO se descartan.
  - Con OR: si una parte es TRUE, el resultado es TRUE.
  - Con AND: si una parte es FALSE, el resultado es FALSE.
  - Con NOT: NOT DESCONOCIDO sigue siendo DESCONOCIDO.

Ejemplo clásico: SELECT * FROM usuarios WHERE telefono = NULL; NO devuelve
nada; lo correcto es WHERE telefono IS NULL.


================================================================================
MÓDULO B5: CONSULTAS Y OPERACIONES BÁSICAS
================================================================================

----------------------------------------------------------
1. Filtrado avanzado con WHERE
----------------------------------------------------------
  - LIKE / ILIKE: coincidencia de patrón con comodines % (cualquier cantidad de
    caracteres) y _ (un solo carácter). ILIKE ignora mayúsculas (PostgreSQL).
        SELECT * FROM usuarios WHERE email LIKE '%@gmail.com';
  - IN: pertenencia a una lista de valores.
        SELECT * FROM usuarios WHERE pais IN ('MX', 'CO', 'AR');
  - BETWEEN: rango inclusivo (funciona para números y fechas).
        SELECT * FROM pedidos WHERE total BETWEEN 100 AND 500;
  - IS NULL / IS NOT NULL: detecta ausencia de valor (ver la lógica tri-valor).
        SELECT * FROM clientes WHERE telefono IS NULL;
  - AND / OR / NOT: combinación de condiciones.

----------------------------------------------------------
2. Ordenamiento (ORDER BY) y limitación (LIMIT / OFFSET)
----------------------------------------------------------
  - ORDER BY columna ASC | DESC: ordena el resultado. Con varias columnas se
    ordena en cascada.
        SELECT * FROM usuarios ORDER BY fecha_registro DESC;
  - LIMIT n: devuelve solo las primeras n filas.
  - OFFSET m: salta las primeras m filas (paginación clásica: página 1 =
    LIMIT 10 OFFSET 0; página 2 = LIMIT 10 OFFSET 10).

Advertencia de paginación: OFFSET se vuelve ineficiente en tablas enormes; el
patrón con WHERE id > ultimo_id (keyset pagination) escala mejor.

----------------------------------------------------------
3. Combinación de tablas: JOINs
----------------------------------------------------------
Permiten ejecutar una consulta sobre varias tablas a la vez usando su relación
(la base del "join").

  - INNER JOIN: Solo las filas que coinciden en ambas tablas (el más usado).
        SELECT u.nombre, p.biografia
        FROM usuarios u
        INNER JOIN perfiles p ON p.id_usuario = u.id;
  - LEFT JOIN (LEFT OUTER JOIN): Todas las filas de la tabla izquierda, más las
    coincidencias de la derecha; si no coincide, las columnas de la derecha
    quedan NULL.
        SELECT u.nombre, p.biografia
        FROM usuarios u
        LEFT JOIN perfiles p ON p.id_usuario = u.id;
  - RIGHT JOIN (RIGHT OUTER JOIN): Lo inverso; todas las filas de la derecha.
  - FULL OUTER JOIN: Todas las filas de ambas tablas; completa con NULL donde
    no hay coincidencia.
  - CROSS JOIN: Producto cartesiano: cada fila de A con cada fila de B, sin
    condición ON. Ejemplo: combinaciones de tallas y colores.

Sintaxis moderna: cuando la columna de unión se llama igual en ambas tablas se
puede usar INNER JOIN ... USING (columna).

MÓDULO I1: NORMALIZACIÓN PROFUNDA
================================================================================

La normalización de bases de datos es un proceso que consiste en designar y
aplicar una serie de reglas a las relaciones obtenidas tras el paso del modelo
entidad-relación al modelo relacional, con el objeto de minimizar la redundancia
de datos y facilitar su gestión posterior.

Objetivos de la normalización:
  - Minimizar la redundancia de los datos.
  - Disminuir los problemas de actualización de los datos en las tablas.
  - Proteger la integridad de los datos.

Para que una tabla pueda considerarse una relación válida debe cumplir ciertas
restricciones: nombre único, sin filas duplicadas y columnas homogéneas (ver
módulo B2).

----------------------------------------------------------
1. Primera Forma Normal (1FN)
----------------------------------------------------------
Reglas:
  - Cada celda contiene UN SOLO valor atómico (nada de listas, arreglos o
    grupos repetidos).
  - No se permiten columnas multivaluadas dentro de una celda.

Ejemplo NO normalizado (viola 1FN):
  pedidos (id, cliente, productos = "Teclado, Mouse, Monitor")
Solución 1FN: dividir en filas, un producto por fila, o crear la tabla
intermedia pedido_producto.

Una tabla en 1FN puede padecer redundancia vía dependencias parciales, que se
resuelven en la 2FN.

----------------------------------------------------------
2. Segunda Forma Normal (2FN)
----------------------------------------------------------
Requiere estar en 1FN Y que NO existan dependencias parciales de la clave:
todo atributo NO clave debe depender de la clave completa (de TODAS las
columnas de la clave primaria), no solo de una parte.

Ejemplo que viola 2FN (clave compuesta):
  pedido_producto (id_pedido, id_producto, nombre_producto, cantidad)
  -> nombre_producto depende solo de id_producto (parte de la clave), no de la
     clave completa.
Solución 2FN: separar en dos tablas:
  productos (id_producto, nombre_producto)
  pedido_producto (id_pedido, id_producto, cantidad)

Nota: la 2FN solo aplica cuando la clave es compuesta (más de una columna).

----------------------------------------------------------
3. Tercera Forma Normal (3FN)
----------------------------------------------------------
Requiere estar en 2FN Y que NO existan dependencias transitivas: ningún
atributo NO clave debe depender de otro atributo NO clave.

Ejemplo que viola 3FN:
  pedidos (id_pedido, id_cliente, nombre_cliente, ciudad_cliente)
  -> nombre_cliente y ciudad_cliente dependen de id_cliente (que es un atributo
     NO clave), no de id_pedido. Redundancia: el nombre del cliente se repite
     en cada pedido.
Solución 3FN: separar en:
  clientes (id_cliente, nombre_cliente, ciudad_cliente)
  pedidos  (id_pedido, id_cliente)

La regla operativa popular: "todo atributo depende de la clave, de toda la
clave y solo de la clave" (resumen de 2FN + 3FN).

----------------------------------------------------------
4. Forma Normal de Boyce-Codd (FNBC / BCNF)
----------------------------------------------------------
Es una versión más estricta de la 3FN. Se aplica cuando una tabla tiene claves
candidatas solapadas (superpuestas).

Regla: para TODA dependencia funcional X -> Y, el lado izquierdo X debe ser una
SUPERCLAVE de la tabla (un conjunto de columnas que identifica unívocamente a
la fila).

Ejemplo que cumple 3FN pero NO FNBC:
  profesores_materias (id_profesor, materia, despacho)
  donde "un profesor tiene un solo despacho" (id_profesor -> despacho) y "cada
  materia la imparte un solo profesor" (materia -> id_profesor). La clave es
  (id_profesor, materia), pero materia -> id_profesor tiene como lado izquierdo
  una columna que NO es superclave.
Solución FNBC: separar en
  profesores (id_profesor, despacho)
  materias   (materia, id_profesor)

En la práctica, la FNBC cubre casos poco frecuentes; la 3FN basta para la
mayoría de los proyectos, pero conocerla evita anomalías de actualización.

Importante: la aplicación es acumulativa - 1FN -> 2FN -> 3FN -> FNBC; cada
forma exige la anterior.

----------------------------------------------------------
5. Denormalización técnica (y cuándo desnormalizar)
----------------------------------------------------------
Desnormalizar es reintroducir INTENCIONALMENTE redundancia (o romper 3FN) para
GANAR velocidad de lectura, aceptando el costo de mantener esa redundancia.

Cuándo conviene:
  - Tablas de reportes / análisis con lecturas masivas.
  - Caché precalculado de agregados (totales, contadores) que se consultan
    millones de veces.
  - Evitar JOINs costosos en consultas calientes de alto tráfico.

Ejemplos típicos:
  - Guardar total_pedido en la tabla pedidos aunque pueda calcularse con SUM de
    las líneas (manteniéndolo al insertar o actualizar).
  - Replicar nombre_cliente en pedidos para no unir siempre con clientes.

Regla profesional: normalizar para escrituras; desnormalizar (de forma
controlada y documentada) para lecturas críticas. Nunca desnormalizar "por si
acaso": cada columna repetida debe mantenerse sincronizada.

----------------------------------------------------------
6. Claves: conceptos generales y tipos
----------------------------------------------------------
- Clave Candidata: cualquier columna o conjunto de columnas que identifica de
  forma unívoca a cada fila de una tabla. Una tabla puede tener varias.
- Clave Alternativa: una clave candidata que no fue elegida como primaria, pero
  que sigue identificando de forma única cada fila. Ejemplo: en CLIENTES con
  primaria id_cliente, el número de Seguro Social es clave alternativa (pudo no
  elegirse por si algún cliente no lo posee).
- Clave Compuesta: clave formada por la unión de dos o más columnas.
- Clave Primaria (PK): el conjunto mínimo de columnas que identifica
  unívocamente a cada fila. Frecuentemente es numérica, auto-incrementada y, por
  convención, la primera columna (no es una obligación técnica). Garantiza la
  integridad de entidad.
- Clave Foránea (FK): columna que existe como dependiente en una tabla y
  referencia la clave primaria de otra, conectando registros y garantizando la
  integridad referencial.

Regla de elección: entre varias claves candidatas, elegir la de menor número de
columnas y la más estable.

Tabla comparativa PK vs FK:
  +--------------------------+-------------------------------------------+
  | Clave Primaria           | Clave Foránea                             |
  +--------------------------+-------------------------------------------+
  | Identifica cada fila     | Referencia la PK de otra tabla            |
  | No admite NULL           | Puede admitir NULL (según regla de negocio)|
  | Única en toda la tabla   | Puede repetirse (muchas filas comparten)  |
  | Una sola por tabla       | Varias por tabla                          |
  | Su valor no debe cambiar | Puede actualizarse si cambia la PK        |
  | PRIMARY KEY              | FOREIGN KEY ... REFERENCES                |
  | Integridad de entidad    | Integridad referencial                    |
  +--------------------------+-------------------------------------------+

Ejemplo con las tablas Usuarios y Perfiles:
  CREATE TABLE usuarios (
     id_usuario    INT PRIMARY KEY AUTO_INCREMENT,
     email         VARCHAR(100) UNIQUE NOT NULL,
     nombre_usuario VARCHAR(50) UNIQUE NOT NULL,
     fecha_registro DATE NOT NULL
  );
  -- Claves: primaria id_usuario; candidatas email y nombre_usuario.

  CREATE TABLE perfiles_usuario (
     id_perfil     INT PRIMARY KEY AUTO_INCREMENT,
     id_usuario    INT NOT NULL,
     biografia     TEXT,
     avatar_url    VARCHAR(255),
     tema_preferido VARCHAR(20) DEFAULT 'claro',
     fecha_actualizacion DATE,
     FOREIGN KEY (id_usuario) REFERENCES usuarios(id_usuario)
        ON DELETE CASCADE
  );
  -- Claves: primaria id_perfil; foránea id_usuario -> usuarios(id_usuario).


================================================================================
MÓDULO I2: AGREGACIÓN Y FUNCIONES DE AGRUPACIÓN
================================================================================

----------------------------------------------------------
1. Funciones de agregación
----------------------------------------------------------
Operan sobre TODAS las filas de un grupo y devuelven UN solo valor por grupo.
Ignoran los NULL (a excepción de COUNT(*)).

  - COUNT(*): número total de filas (incluye los NULL).
    COUNT(col): filas con valor no nulo. COUNT(DISTINCT col): valores únicos.
  - SUM(col): suma numérica.
  - AVG(col): promedio numérico.
  - MIN(col): valor mínimo (numérico, fecha o texto).
  - MAX(col): valor máximo.

        SELECT COUNT(*) AS total_pedidos,
               SUM(total) AS facturado,
               AVG(total) AS ticket_promedio,
               MIN(total) AS minimo,
               MAX(total) AS maximo
        FROM pedidos;

En PostgreSQL puede combinarse con FILTER (WHERE ...) para agregados
condicionales sin subconsultas:
  SUM(total) FILTER (WHERE estado = 'pagado')

----------------------------------------------------------
2. GROUP BY
----------------------------------------------------------
Divide las filas en grupos según el valor de una o varias columnas y aplica las
agregaciones A CADA GRUPO.

        SELECT pais, COUNT(*) AS usuarios, AVG(edad)
        FROM usuarios
        GROUP BY pais;

Reglas:
  - Toda columna del SELECT que no esté dentro de una función de agregación
    debe aparecer en el GROUP BY.
  - El GROUP BY actúa después de que el WHERE haya filtrado filas.

----------------------------------------------------------
3. HAVING vs WHERE (diferencia fundamental)
----------------------------------------------------------
  - WHERE filtra FILAS ANTES de agruparse; no puede usar funciones de
    agregación ni alias.
  - HAVING filtra GRUPOS DESPUÉS de agruparse; sí puede usar COUNT, SUM, etc.

        SELECT pais, COUNT(*) AS usuarios
        FROM usuarios
        WHERE fecha_registro > '2024-01-01'   -- filtra filas primero
        GROUP BY pais
        HAVING COUNT(*) >= 5;                 -- filtra grupos después

Orden lógico de ejecución de una consulta:
  FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT.
Por eso el WHERE no "ve" los agregados calculados en el SELECT.


================================================================================
MÓDULO I3: RESTRICCIONES DE INTEGRIDAD (CONSTRAINTS)
================================================================================

Las restricciones son reglas impuestas por el SGBD que garantizan que los datos
que entran cumplan las condiciones del negocio. Se declaran en el esquema.

----------------------------------------------------------
1. Constraints básicas
----------------------------------------------------------
  - NOT NULL: la columna no puede quedar vacía (obligatoria).
        email VARCHAR(100) NOT NULL
  - UNIQUE: no se permiten valores repetidos (en la mayoría de SGBD permite
    varios NULL). Puede aplicarse a una columna o a un conjunto de columnas.
        email VARCHAR(100) UNIQUE
        UNIQUE (id_usuario, rol)   -- unicidad compuesta
  - CHECK: valida una condición booleana sobre el valor insertado/modificado.
        CHECK (edad >= 0 AND edad <= 120)
        CHECK (fecha_fin > fecha_inicio)
  - DEFAULT: valor que se asigna a la columna si el INSERT no la menciona.
        tema_preferido VARCHAR(20) DEFAULT 'claro'
        fecha_creacion TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
  - PRIMARY KEY = NOT NULL + UNIQUE (de forma implícita).
  - FOREIGN KEY: hace referencia a otra tabla.

Comandos útiles para tablas existentes:
  ALTER TABLE ... ADD CONSTRAINT ... / DROP CONSTRAINT ...

----------------------------------------------------------
2. Acciones referenciales en claves foráneas (ON DELETE / ON UPDATE)
----------------------------------------------------------
Definen qué hacer con las filas dependientes cuando la fila referenciada se
borra o se actualiza.

  - ON DELETE CASCADE: al borrar la fila padre, se borran AUTOMÁTICAMENTE las
    filas hijas. Lógico para relaciones de pertenencia estricta (el perfil de
    un usuario, las líneas de un pedido).
  - ON DELETE SET NULL: al borrar el padre, las FK hijas pasan a NULL (exige
    que la columna FK permita NULL). Sirve para "desvincular pero conservar".
  - ON DELETE RESTRICT: impide el borrado del padre si existen hijas (rechaza
    con error; en PostgreSQL se evalúa de inmediato dentro de la misma
    sentencia).
  - ON DELETE NO ACTION: comportamiento por defecto; también impide el borrado,
    con diferencias en el momento de evaluación según el SGBD (en la práctica
    muy parecido a RESTRICT).
  - ON UPDATE CASCADE: actualiza las FK hijas cuando cambia el valor de la PK
    referenciada.

Resumen de elección:
  - El hijo no tiene vida propia  -> CASCADE (perfiles, detalle de pedido).
  - El hijo debe conservarse aunque se elimine el padre  -> SET NULL.
  - No se permite eliminar datos referenciados  -> RESTRICT / NO ACTION.

        CREATE TABLE pedido_item (
          id_pedido   INT REFERENCES pedidos(id)   ON DELETE CASCADE,
          id_producto INT REFERENCES productos(id) ON DELETE RESTRICT
        );

================================================================================
MÓDULO I4: VISTAS Y SUBCONSULTAS
================================================================================

----------------------------------------------------------
1. Subconsultas (no correlacionadas vs correlacionadas)
----------------------------------------------------------
Una subconsulta es un SELECT anidado dentro de otra consulta (en WHERE, FROM,
SELECT o HAVING).

  - No correlacionada: se evalúa UNA sola vez, de forma independiente, y su
    resultado no cambia por fila. Puede devolver un escalar, una lista (para
    IN) o una tabla (en FROM).
        SELECT * FROM pedidos
        WHERE id_cliente IN (SELECT id FROM clientes WHERE pais = 'ES');

  - Correlacionada: se evalúa UNA VEZ POR FILA de la consulta externa, porque
    hace referencia a columnas de esa consulta externa (alias).
        SELECT u.nombre, u.email
        FROM usuarios u
        WHERE EXISTS (
          SELECT 1 FROM pedidos p
          WHERE p.id_usuario = u.id AND p.total > 1000
        );

  EXISTS vs IN:
  - IN: compara contra una lista de valores (cuidado con NULL: si la
    subconsulta devuelve NULL, el IN puede no devolver nada).
  - EXISTS: solo comprueba la EXISTENCIA de filas; es la opción más eficiente
    para "tiene al menos un registro relacionado" y suele rendir mejor que IN
    cuando la lista es grande.

Operadores de subconsulta: IN, NOT IN, EXISTS, NOT EXISTS, y comparaciones con
ANY / SOME / ALL:
  - WHERE precio > ALL (SELECT precio FROM promos)  => mayor que todas.
  - WHERE precio > ANY (SELECT precio FROM promos)  => mayor que al menos una.

----------------------------------------------------------
2. Vistas (Views)
----------------------------------------------------------
Una vista es una consulta SQL almacenada con nombre; se consulta como si fuera
una tabla, pero NO guarda datos: es una "tabla virtual".

  - Vista simple: sobre una sola tabla; normalmente se puede ACTUALIZAR a
    través de ella (insertar o editar filas de la tabla subyacente).
  - Vista materializada: GUARDA FÍSICAMENTE el resultado de la consulta. Es
    muy rápida de leer porque no recalcula, pero los datos pueden quedar
    desactualizados y hay que refrescarla manualmente (REFRESH MATERIALIZED
    VIEW en PostgreSQL). Uso típico: reportes pesados y agregados
    precalculados.

        CREATE VIEW clientes_activos AS
        SELECT id, email FROM usuarios WHERE activo = TRUE;

        CREATE MATERIALIZED VIEW resumen_ventas AS
        SELECT producto_id, SUM(cantidad) AS total
        FROM lineas GROUP BY producto_id;

Cuándo usar cada una: las vistas simples sirven para seguridad (exponer solo
las columnas permitidas) y para reutilizar consultas; las materializadas, para
render de analítica pesada.


================================================================================
MÓDULO I5: ESTRATEGIAS Y ESTRUCTURAS DE ÍNDICES
================================================================================

Un índice es una estructura de datos que mejora la velocidad de las operaciones
de búsqueda y consulta en una tabla. Se puede pensar en un índice como el índice
de un libro: permite encontrar información sin revisar cada página.

----------------------------------------------------------
1. Concepto y funcionamiento
----------------------------------------------------------
Un índice guarda una copia ORDENADA de ciertas columnas, junto con un puntero a
la fila correspondiente en la tabla original. Cuando se ejecuta una consulta, el
SGBD puede usar el índice en lugar de escanear toda la tabla (full table scan).

Estructuras de datos usadas por los SGBD:
  - Árboles B (B-tree): mantienen los datos en orden; ideales para búsquedas,
    rangos, ORDER BY y agrupaciones. Es el estándar en PostgreSQL y MySQL.
  - Hashing: búsquedas de igualdad exacta muy rápidas; no sirve para rangos.
  - Bitmap: en bases de datos analíticas, para columnas con pocos valores
    distintos.

Sin índice, el SGBD lee TODAS las filas (lectura secuencial / escaneo
completo). Con índice, la búsqueda requiere un número logarítmico de pasos y el
tiempo se reduce drásticamente en tablas grandes.

Ejemplo con la tabla Libros:
  id  titulo               autor                      año
  1   Don Quijote          Miguel de Cervantes        1605
  2   Cien Años de Soledad Gabriel García Márquez     1967
  3   Hamlet               William Shakespeare        1603
  4   La Odisea            Homero                     -700
  5   Matar a un Ruiseñor  Harper Lee                 1960

  SELECT * FROM Libros WHERE autor = 'Homero';
  CREATE INDEX idx_autor ON Libros(autor);

Con el índice idx_autor (estructura ordenada), el SGBD localiza 'Homero' y
sigue el puntero al registro, sin revisar las demás filas.

Ventajas de los índices: aceleran SELECT, filtros, JOINs y ordenamientos.
Desventajas: ocupan espacio en disco y ralentizan INSERT / UPDATE / DELETE
porque cada escritura debe mantener los índices; un exceso de índices puede
contrarrestar sus beneficios.

Cuándo usar índices:
  - En columnas utilizadas con frecuencia en WHERE, JOIN u ORDER BY.
  - En columnas con alta cardinalidad (muchos valores únicos).
  - NO en tablas pequeñas ni en columnas con pocos valores distintos.

Un buen diseño de índices es clave para optimizar el rendimiento de una base de
datos.

Tipos de índices (recap del nivel):
  Índice primario (sobre la PK), índice único, índice compuesto (varias
  columnas), índice de texto completo, índice agrupado y no agrupado.

Para consultar los índices creados en PostgreSQL, ver la guía de PostgreSQL.

----------------------------------------------------------
2. Índice agrupado (Clustered) vs no agrupado (Non-Clustered)
----------------------------------------------------------
  - Clustered (agrupado): reordena FÍSICAMENTE las filas de la tabla según el
    índice. La tabla ES el índice. Solo puede existir UNO (típicamente la clave
    primaria en MySQL/InnoDB y SQL Server). Acceso rapidísimo por rango de la
    clave, pero mover una fila implica reordenar física (escrituras más
    costosas). Analogía: una agenda telefónica ordenada por apellido.
  - Non-Clustered (no agrupado): es una estructura ordenada SEPARADA que apunta
    a las filas (a través del índice agrupado o de la dirección física). Puede
    haber muchos por tabla. No reordena la tabla. Analogía: el índice de
    materias al final de un libro, que te lleva a la página.

Nota PostgreSQL: no tiene el concepto de "clustered" como SQL Server/MySQL;
internamente usa un HEAP (datos apilados sin orden físico) más tantos índices
no agrupados como se quieran, y el comando CLUSTER permite reordenar la tabla
físicamente según un índice.

----------------------------------------------------------
3. Índices parciales e índices de cobertura
----------------------------------------------------------
  - Índice parcial: se crea sobre un SUBCONJUNTO de filas mediante WHERE.
    Ocupa menos espacio y acelera las consultas que siempre filtran por el
    mismo predicado.
        CREATE INDEX idx_pedidos_activos ON pedidos (total)
        WHERE estado = 'activo';
  - Índice de cobertura (Covering Index): incluye TODAS las columnas que la
    consulta necesita, de modo que el SGBD puede responder SIN tocar la tabla
    (Index Only Scan). En PostgreSQL se añade con INCLUDE.
        CREATE INDEX idx_cubridor ON pedidos (id_usuario)
        INCLUDE (total, estado);
    Con él, SELECT total, estado WHERE id_usuario = X solo lee el índice. Las
    columnas INCLUDE no participan en la búsqueda, pero se guardan junto a cada
    entrada.

Consideraciones: los índices de cobertura aceleran lecturas a cambio de espacio
y escrituras más pesadas; úsalos en consultas que se ejecutan millones de veces.

----------------------------------------------------------
4. Ejemplo de índice con Django
----------------------------------------------------------
Un índice de base de datos funciona como el índice de un libro: en lugar de
leer todas las páginas de la tabla (full table scan) para encontrar un
registro, la base de datos consulta una estructura ordenada (generalmente un
árbol B) que la lleva directamente al resultado.

1. Define el modelo con y sin índice (db_index=True solo en lo que se quiere
   optimizar):
     from django.db import models
     class Cliente(models.Model):
         # Campo SIN índice
         email = models.EmailField()
         # Campo CON índice
         codigo_cliente = models.CharField(max_length=50, db_index=True)

   Aplica los cambios:
     $ python manage.py makemigrations
     $ python manage.py migrate

2. Genera datos masivos de prueba (100.000 registros en manage.py shell):
     import uuid
     from myapp.models import Cliente
     objetos = [
         Cliente(email=f"usuario_{i}@ejemplo.com",
                 codigo_cliente=str(uuid.uuid4()))
         for i in range(100000)
     ]
     Cliente.objects.bulk_create(objetos)

3. Mide el tiempo de consulta en ambos campos:
     import time
     from myapp.models import Cliente
     ultimo = Cliente.objects.last()
     inicio = time.time()
     res1 = Cliente.objects.filter(email=ultimo.email).first()
     t_sin = time.time() - inicio
     inicio = time.time()
     res2 = Cliente.objects.filter(codigo_cliente=ultimo.codigo_cliente).first()
     t_con = time.time() - inicio
     print(f"Sin índice: {t_sin:.5f} s")
     print(f"Con índice: {t_con:.5f} s")

4. Inspecciona el plan de búsqueda (EXPLAIN) para ver Scan vs Index Scan:
     print(Cliente.objects.filter(email=ultimo.email).explain())
     print(Cliente.objects.filter(codigo_cliente=ultimo.codigo_cliente).explain())

Resultado esperado:
  - Sin índice: el motor recorre los 100.000 registros uno por uno; el tiempo
    tarda desde varios milisegundos en adelante según la base de datos.
  - Con índice: la búsqueda toma un número logarítmico de pasos (O(log N)); el
    tiempo suele reducirse prácticamente a 0.000 s.

MÓDULO I6: SGBD RELACIONALES DEL MERCADO Y NoSQL (COMPARATIVA)
================================================================================

----------------------------------------------------------
1. SGBD relacionales principales
----------------------------------------------------------
  - PostgreSQL: Open source, la referencia de funciones avanzadas (window
    functions, JSONB, extensiones, PL/pgSQL, materialized views). ACID
    estricto, robusto y extensible. Estándar de facto para proyectos
    empresariales.
  - MySQL / MariaDB: Open source, muy difundido, rápido y sencillo (stack
    LAMP/LEMP). MySQL pertenece a Oracle; MariaDB es su fork comunitario.
    Ideal para aplicaciones web clásicas, CRUDs y CMS (WordPress).
  - SQLite: Motor embebido SIN servidor: la base de datos es un solo archivo.
    Cero instalación y cero red. Perfecto para apps móviles, herramientas
    locales, prototipos o el navegador (Firefox lo usa). NO recomendado para
    concurrencia multiusuario intensa en red.
  - Microsoft SQL Server: Comercial de Microsoft. Excelente integración con el
    ecosistema .NET/Windows y con BI (SSRS, SSIS); usa T-SQL.
  - Oracle Database: Comercial y clásico del mundo empresarial. Muy potente en
    grandes corporaciones y banca (PL/SQL, RAC, particionamiento avanzado).
    Licenciamiento costoso y complejidad alta.

Casos de uso resumidos:
  - SQLite  -> local/móvil/embebido y arranque rápido de proyectos.
  - PostgreSQL -> empresarial, estándar del sector, datos exigentes y análisis.
  - MySQL/MariaDB -> web masiva clásica y stack LAMP.
  - SQL Server -> entornos corporativos Windows/.NET.
  - Oracle -> grandes sistemas transaccionales y banca.

Criterios de comparación entre SGBD: licencia y costo, concurrencia y niveles
de aislamiento, tipos de datos, lenguaje de procedimientos (PL/pgSQL vs T-SQL
vs PL/SQL), herramientas y comunidad, rendimiento bajo carga.

----------------------------------------------------------
2. Bases de Datos NoSQL (comparativa con el modelo relacional)
----------------------------------------------------------
NoSQL (a veces llamado "no solo SQL") es una amplia clase de sistemas de
gestión de bases de datos que difieren del modelo clásico de SGBDR en aspectos
importantes: no usan SQL como lenguaje principal, los datos no requieren
estructuras fijas de tablas, normalmente no soportan JOIN ni garantizan ACID
completo, y suelen escalar horizontalmente.

Crecieron con las grandes empresas de internet (Google, Amazon, Twitter,
Facebook), que priorizaban el rendimiento en tiempo real sobre la coherencia
estricta de los modelos relacionales.

Ventajas:
  - Escalabilidad horizontal (responden a la necesidad de las empresas de
    escalar de forma sencilla).
  - Manejo de enormes cantidades de datos sin cuellos de botella.
  - Diferentes motores NoSQL adecuados a diferentes problemas.

Desventajas:
  - Limitaciones para inteligencia de negocio / minería de datos rigurosa.
  - Escasez de profesionales con experiencia (en comparación con el mundo
    relacional).
  - Poca estandarización: cada motor tiene su propia API, sus consultas y sus
    peculiaridades, por lo que migrar de un proveedor a otro es difícil.

Marcas conocidas y su tipo:
  - MongoDB: documental. Guarda documentos tipo JSON, muy flexible, pensada
    para alta escalabilidad y miles de lecturas por segundo.
  - Apache Cassandra: clave-valor/columnar, distribuida sin un único punto de
    fallo (usada entre otros por Facebook); gran volumen distribuido entre
    nodos.
  - Redis: clave-valor en memoria (caché, colas, sesiones); también puede
    usarse como base de datos persistente.
  - Neo4j: orientada a grafos; excelente para datos con altos niveles de
    interrelación (redes sociales, recomendaciones).
  - HBase / BigTable: tabulares columnares, pensadas para datos dispersos a
    gran escala.

Tipos de bases de datos NoSQL:
  - Documentales: cada registro vive en un documento semiestructurado (MongoDB,
    CouchDB).
  - Orientadas a grafos: representan datos como nodos y aristas (Neo4j,
    HyperGraphDB).
  - Clave/valor: pares clave-valor simples y escalables (Redis, Cassandra,
    DynamoDB, Riak).
  - Multivalor: esquemas flexibles con listas de valores (OpenQM, Caché).
  - Tabulares/columnas: grandes volúmenes de datos dispersos (HBase, BigTable).
  - De arrays: malla regular multidimensional para simulaciones, sensores y
    datos estadísticos (SciDB).

Ejemplo de flexibilidad NoSQL (MongoDB): en una misma colección "personas"
puede haber documentos con estructura distinta:
  { Nombre: "José", Apellidos: "Pérez Campo", Edad: 35,
    Aficiones: ["vino", "libros", "ciclismo"],
    Amigos: [ { Nombre: "María", Edad: 22 }, { Nombre: "Luis", Edad: 28 } ] }
  { Nombre: "Luis", Estudios: "Marketing y Publicidad", Amigos: 12 }
En un modelo relacional clásico esto sería imposible sin definir un esquema
fijo; esa flexibilidad es una de las grandes ventajas de NoSQL.

MÓDULO A1: CONSULTAS AVANZADAS Y ANALÍTICA
================================================================================

----------------------------------------------------------
1. Funciones de Ventana (Window Functions)
----------------------------------------------------------
Las funciones de ventana calculan valores sobre un "conjunto de filas
relacionadas" con la fila actual, pero sin colapsar el resultado (a diferencia
de GROUP BY, que devuelve una sola fila por grupo). Se usan con la cláusula
OVER.

Sintaxis general:
  funcion_ventana() OVER (PARTITION BY columna ORDER BY columna)

Partes:
  - PARTITION BY: divide los datos en ventanas (como GROUP BY, pero manteniendo
    todas las filas).
  - ORDER BY dentro de OVER: ordena las filas dentro de cada partición para que
    la función tenga un orden definido.

Funciones principales:
  - ROW_NUMBER(): asigna un número secuencial (1, 2, 3...) a cada fila dentro
    de su partición, sin empates.
        SELECT nombre, salario,
               ROW_NUMBER() OVER (ORDER BY salario DESC) AS puesto
        FROM empleados;
  - RANK(): como ROW_NUMBER pero SÍ EMPATA: si dos filas empatan, reciben el
    mismo rango y hay saltos (1, 2, 2, 4...).
  - DENSE_RANK(): como RANK pero SIN saltos (1, 2, 2, 3...).
  - LAG(columna, n): accede al valor de la fila n posiciones ANTERIORES dentro
    de la partición.
  - LEAD(columna, n): accede al valor de la fila n posiciones POSTERIORES.

        SELECT mes, facturado,
               LAG(facturado, 1) OVER (ORDER BY mes) AS facturado_anterior,
               facturado - LAG(facturado, 1) OVER (ORDER BY mes) AS variacion
        FROM reporte_mensual;

Uso práctico: clasificación, ranking, cálculo de variación entre periodos,
detección de duplicados (ROW_NUMBER() OVER (PARTITION BY col ORDER BY id)).

----------------------------------------------------------
2. Expresiones de Tabla Común - CTEs (Common Table Expressions)
----------------------------------------------------------
Una CTE es una consulta auxiliar definida con WITH al inicio de una consulta;
simplifica la lectura al dividir consultas complejas en bloques con nombre.

Sintaxis:
  WITH cte_nombre AS (
    SELECT columna, ...
    FROM tabla
    WHERE condicion
  )
  SELECT ...
  FROM cte_nombre;

  WITH clientes_activos AS (
    SELECT id, email, nombre
    FROM usuarios WHERE activo = TRUE
  )
  SELECT c.email, COUNT(p.id) AS num_pedidos
  FROM clientes_activos c
  INNER JOIN pedidos p ON p.id_usuario = c.id
  GROUP BY c.email;

Las CTEs pueden anidarse varias veces, creando una "línea de procesamiento"
más legible que subconsultas anidadas en FROM.

----------------------------------------------------------
3. CTEs recursivas (para estructuras jerárquicas: árboles, categorías)
----------------------------------------------------------
Una CTE recursiva se llama a sí misma repetidamente hasta agotar los datos. Es
la herramienta estándar para recorrer jerarquías (organigramas, categorías de
producto, comentarios anidados).

Ejemplo: recorrer un árbol de categorías con campo padre:
  WITH RECURSIVE jerarquia AS (
    -- Caso base: las categorías raíz (sin padre)
    SELECT id, nombre, padre_id, 0 AS nivel
    FROM categorias WHERE padre_id IS NULL
    UNION ALL
    -- Caso recursivo: las hijas de las ya encontradas
    SELECT c.id, c.nombre, c.padre_id, j.nivel + 1
    FROM categorias c
    INNER JOIN jerarquia j ON c.padre_id = j.id
  )
  SELECT * FROM jerarquia ORDER BY nivel, nombre;

Nota: el RECURSIVE es obligatorio en PostgreSQL y otros SGBD modernos; en
algunos motores (MySQL 8+) funciona igual.


================================================================================
MÓDULO A2: LÓGICA EN EL SERVIDOR DE BASE DE DATOS
================================================================================

Los SGBD relacionales permiten ejecutar lógica de negocio directamente dentro
del servidor, reduciendo la ida y vuelta con la aplicación.

----------------------------------------------------------
1. Procedimientos Almacenados (Stored Procedures)
----------------------------------------------------------
Bloques de código con nombre, guardados en la BD y ejecutables con CALL o con
la sintaxis específica del motor. Pueden recibir parámetros IN, OUT e INOUT.

PostgreSQL (PL/pgSQL):
  CREATE OR REPLACE PROCEDURE actualizar_estado(pedido_id INT, nuevo_estado TEXT)
  LANGUAGE plpgsql
  AS $$
  BEGIN
    UPDATE pedidos SET estado = nuevo_estado WHERE id = pedido_id;
    COMMIT;
  END;
  $$;
  CALL actualizar_estado(101, 'pagado');

SQL Server (T-SQL):
  CREATE PROCEDURE sp_ActualizarEstado @PedidoId INT, @NuevoEstado NVARCHAR(20)
  AS
  BEGIN
    UPDATE pedidos SET estado = @NuevoEstado WHERE id = @PedidoId;
  END;
  EXEC sp_ActualizarEstado 101, 'pagado';

Ventajas: encapsulan lógica compleja, reducen tráfico de red, aprovechan la
optimización del plan del motor y facilitan auditoría centralizada.

----------------------------------------------------------
2. Funciones definidas por el usuario (User-Defined Functions)
----------------------------------------------------------
Similar a los procedimientos pero devuelven un valor (escalar o tabla) y pueden
usarse dentro de un SELECT.

  CREATE OR REPLACE FUNCTION precio_con_iva(precio NUMERIC)
  RETURNS NUMERIC
  LANGUAGE SQL
  AS $$
    SELECT precio * 1.21;
  $$;

  SELECT nombre, precio_con_iva(precio) FROM productos;

Diferencia con procedimientos: las funciones pueden invocarse dentro de SELECT,
WHERE y expresiones; los procedimientos ejecutan acciones y no deben usarse
dentro de una consulta.

----------------------------------------------------------
3. Disparadores (Triggers)
----------------------------------------------------------
Bloques de código que se ejecutan AUTOMÁTICAMENTE antes, después o en lugar
de una operación INSERT, UPDATE o DELETE en una tabla.

  CREATE OR REPLACE FUNCTION log_cambio_estado()
  RETURNS TRIGGER
  LANGUAGE plpgsql
  AS $$
  BEGIN
    INSERT INTO auditoria(id_pedido, estado_anterior, estado_nuevo, fecha)
    VALUES (OLD.id, OLD.estado, NEW.estado, NOW());
    RETURN NEW;
  END;
  $$;

  CREATE TRIGGER trg_estado_pedido
  AFTER UPDATE OF estado ON pedidos
  FOR EACH ROW
  WHEN (OLD.estado IS DISTINCT FROM NEW.estado)
  EXECUTE PROCEDURE log_cambio_estado();

Eventos:
  - BEFORE: se ejecuta ANTES de la operación; puede modificar NEW o cancelar la
    operación con RETURN NULL.
  - AFTER: se ejecuta DESPUÉS de que la operación fue confirmada. Ideal para
    registros de auditoría.
  - INSTEAD OF: reemplaza la operación en vistas que de otro modo no serían
    actualizables.

Cuándo usar triggers: auditoría, validaciones complejas, sincronización entre
tablas, actualización de columnas derivadas. Precaución: el código dentro de
un trigger puede ser difícil de depurar y causar efectos colaterales.


================================================================================
MÓDULO A3: CONTROL DE CONCURRENCIA Y AISLAMIENTO (TRANSACCIONES)
================================================================================

----------------------------------------------------------
1. Las propiedades ACID (repaso profundo)
----------------------------------------------------------
Cuando se dice que un SGBD es ACID-compliant, indica que sus transacciones
cumplen cuatro propiedades fundamentales:

  - Atomicidad: cada transacción es una unidad indivisible. O bien se ejecutan
    TODOS sus pasos, o no se ejecuta ninguno.
  - Consistencia: antes de la transacción la BD está en un estado válido; tras
    la transacción sigue en un estado válido (no rompe reglas de integridad).
  - Aislamiento: una operación concurrente no puede observar los cambios
    parciales de otra transacción en curso. El nivel de aislamiento define
    cuándo y cómo se hacen visibles los cambios entre transacciones.
  - Durabilidad: una vez que la transacción ha sido confirmada (COMMIT), sus
    cambios persisten aunque falle el sistema (gracias a los registros de
    seguridad / WAL).

Cumpliendo estos cuatro requisitos, un SGBD puede considerarse ACID-compliant.

----------------------------------------------------------
2. Niveles de aislamiento de transacciones
----------------------------------------------------------
El estándar SQL define cuatro niveles, de menor a mayor aislamiento:

  - Read Uncommitted (no Committed): puede leer datos modificados pero aún no
    confirmados por otra transacción (permite dirty reads).
  - Read Committed (Committed): solo lee datos confirmados. Es el nivel por
    defecto en PostgreSQL y SQL Server. Evita dirty reads pero NO las no
    repetibles.
  - Repeatable Read (Repetible garantizado): una segunda lectura de la misma
    fila dentro de la transacción devolverá SIEMPRE el mismo valor. Evita
    dirty reads y non-repeatable reads.
  - Serializable (Serializable): el nivel más alto. Simula que las
    transacciones se ejecutan una detrás de otra (serial), evitando todos los
    problemas conocidos.

----------------------------------------------------------
3. Problemas de concurrencia
----------------------------------------------------------
  - Dirty Read (Lectura sucia): lee un dato que otra transacción modificó pero
    AÚN NO ha confirmado. Si esa otra transacción hace ROLLBACK, el dato
    leído nunca existió.
  - Non-Repeatable Read (Lectura no repetible): dentro de la misma
    transacción, leer la misma fila dos veces produce resultados diferentes
    porque otra transacción la actualizó y confirmó entre ambas lecturas.
  - Phantom Read (Lectura fantasma): una segunda ejecución de la misma consulta
    dentro de la transacción devuelve FILAS NUEVAS que aparecieron porque otra
    transacción hizo INSERT y COMMIT.

----------------------------------------------------------
4. Mecanismos de bloqueo (Locking)
----------------------------------------------------------
  - Bloqueo pesimista (Pessimistic): asume que las colisiones OCURREN y bloquea
    los registros ANTES de modificarlos. Es el mecanismo tradicional.
      SELECT ... FOR UPDATE: bloquea las filas seleccionadas hasta el fin de la
      transacción, impidiendo que otras transacciones las modifiquen.
  - Bloqueo optimista (Optimistic): permite que varias transacciones lean y
    modifiquen los datos sin bloquearlos, pero al confirmar verifica si hubo
    conflictos (por ejemplo, usando una columna de versión o timestamp). Si
    hubo conflicto, la transacción se reintenta. Es más eficiente en entornos
  de lectura intensiva con pocos conflictos.

  Con FOR UPDATE (PostgreSQL):
      BEGIN;
      SELECT * FROM pedidos WHERE id = 1 FOR UPDATE;   -- bloquea esa fila
      UPDATE pedidos SET estado = 'pagado' WHERE id = 1;
      COMMIT;


================================================================================
MÓDULO A4: RENDIMIENTO Y DIAGNÓSTICO
================================================================================

----------------------------------------------------------
1. Lectura profunda de planes de ejecución (EXPLAIN / EXPLAIN ANALYZE)
----------------------------------------------------------
EXPLAIN muestra el plan que el optimizador elegiría para ejecutar la consulta,
sin ejecutarla. EXPLAIN ANALYZE ejecuta la consulta de verdad y muestra el
tiempo real, siendo la herramienta definitiva de diagnóstico.

  EXPLAIN SELECT * FROM pedidos WHERE id_usuario = 42;

Plan típico de PostgreSQL (simplificado):
  Index Scan using idx_pedidos_usuario on pedidos
    Index Cond: (id_usuario = 42)
  Planning Time: 0.03 ms
  Execution Time: 0.02 ms

Tipos de acceso que conviene distinguir:
  - Seq Scan (Sequential Scan): lee TODA la tabla. Usado cuando el optimizador
    estima que es más barato que cualquier índice (tablas pequeñas, predicción
    de que se devolverán muchas filas).
  - Index Scan: usa un índice para localizar las filas y luego accede a la
    tabla por la dirección guardada en el índice.
  - Index Only Scan: la consulta se resuelve SIN acceder a la tabla (solo lee
    el índice). Ocurre con índices de cobertura que contienen todas las
    columnas necesarias.
  - Bitmap Index Scan + Bitmap Heap Scan: combina dos pasos; útil cuando el
    índice cumple parcialmente el predicado.

Parámetros importantes en el plan:
  - rows (estimated): estimación del optimizador sobre el número de filas.
  - actual time (en ANALYZE): tiempo real de ejecución de ese nodo.
  - loops: cuántas veces se ejecutó ese nodo (plan con bucle anidado, por
    ejemplo).

Regla práctica: si ves Seq Scan en una tabla grande, valora si un índice puede
mejorarlo (columnas del WHERE con alta cardinalidad, índices parciales o de
cobertura).

----------------------------------------------------------
2. Métricas de mantenimiento (PostgreSQL)
----------------------------------------------------------
  - VACUUM: libera el espacio de filas obsoletas (dead tuples) que quedan
    después de UPDATE/DELETE. Sin él, la tabla crece indefinidamente y las
    lecturas se degradan.
      VACUUM;              -- liberar espacio (sin reorganizar disco)
      VACUUM FULL;         -- reorganiza físicamente (requiere bloqueo)
      VACUUM ANALYZE;      -- libera espacio y actualiza las estadísticas
  - ANALYZE: actualiza las estadísticas que el optimizador usa para elegir
    planes de ejecución. Sin ANALYZE, el optimizador puede tomar decisiones
    erróneas basadas en datos antiguos.
  - autovacuum: daemon de PostgreSQL que ejecuta VACUUM automáticamente; está
    habilitado por defecto y es fundamental para mantener el rendimiento.
  - Fragmentación de índices: tras muchas escrituras, los índices pueden
    fragmentarse y perder eficiencia. En MySQL/InnoDB se corrige con OPTIMIZE
    TABLE; en PostgreSQL, REINDEX.

----------------------------------------------------------
3. Pool de conexiones (connection pooling)
----------------------------------------------------------
Cada conexión a la BD es un proceso con memoria y recursos dedicados; abrir y
cerrar conexiones es costoso. Un pool mantiene un conjunto de conexiones
abiertas reutilizables.

  - PgBouncer: pool ligero y ampliamente usado para PostgreSQL. Se ejecuta como
    proxy entre la aplicación y el servidor. Modos: session (libera la conexión
    al cerrar sesión), transaction (la devuelve al pool al terminar cada
    transacción) y statement (el más restrictivo, sin uso práctico real).
  - HikariCP: pool integrado en el lado de la aplicación JVM (usado por
    Spring Boot y JDBC). No necesita proceso separado.

Buena práctica: fijar un límite razonable de conexiones (no ilimitado); un
exceso de conexiones simultáneas ralentiza el motor de base de datos.


================================================================================
MÓDULO A5: ESCALABILIDAD Y ALTA DISPONIBILIDAD
================================================================================

Cuando una única instancia de SGBD no alcanza el volumen o la disponibilidad
requeridos, se recurre a estrategias de distribución y redundancia.

----------------------------------------------------------
1. Estrategias de replicación
----------------------------------------------------------
  - Replicación síncrona: cada escritura se confirma SOLO cuando TODOS los
    nodos la han aceptado. Garantiza que un nodo espejo siempre tenga los
    mismos datos (RPO = 0), pero es más lenta (depende de la latencia de red).
    Uso: transacciones críticas donde la pérdida de datos es inaceptable.
  - Replicación asíncrona: el nodo primario confirma la escritura y la replica
    después, sin esperar la respuesta del espejo. Es más rápida pero un fallo
    del primario antes de replicar puede significar pérdida de datos recientes.
    Uso: la mayoría de los sistemas web convencionales.
  - Replicación lógica: replicación a nivel de FILAS usando datos
    serializados (por ejemplo, secuencias de cambios de tipo WAL convertidos a
    SQL). Permite replicar entre distintas versiones o configuraciones.
  - Replicación física: replicación del archivo de datos a nivel de bloque.
    Es más rápida pero exige que ambas instancias sean idénticas.
  - Máster-Esclavo (Primary / Replica): un nodo acepta escrituras (el
    "primario") y uno o más espejos son de solo lectura. Si el primario falla,
    un esclavo se promueve a primario.
  - Multi-Máster: varios nodos aceptan escrituras simultáneamente. Más
    complejo de gestionar porque puede haber conflictos entre escrituras
    concurrentes en nodos distintos.

----------------------------------------------------------
2. Particionamiento de tablas
----------------------------------------------------------
Particionar es dividir una tabla LÓGICAMENTE en partes más pequeñas (particiones)
que permanecen dentro de la misma base de datos, pero que el motor maneja de
forma independiente en las búsquedas.

  - Por rango (Range): cada partición cubre un rango de valores. Ideal para
    fechas: particiones por mes o año.
        CREATE TABLE ventas (
          fecha DATE,
          total NUMERIC
        ) PARTITION BY RANGE (fecha);

  - Por lista (List): cada partición contiene un conjunto explícito de valores.
    Útil para multinacionales con partición por país.
  - Por hash (Hash): distribuye los datos según una función hash de una columna.
    Útil para balancear la carga sin un criterio de rango o lista claro.

Ventajas del particionamiento: reduce el tamaño de los índices (cada partición
tiene los suyos), acelera las consultas que filtran por la columna de
partición (el optimizador descarta particiones irrelevantes) y facilita la
limpieza de datos antiguos (DROP PARTITION).

----------------------------------------------------------
3. Patrones de Sharding
----------------------------------------------------------
Sharding es la distribución de datos entre múltiples INSTANCIAS DE BASE DE
DATOS diferentes (distinto servidores), cada una con su propio esquema o datos
diferentes (a diferencia del particionamiento, que es intra-instancia).

Sharding en bases de datos relacionales:
  - El cliente define la lógica de partición (por tenant, por región, por
    hash de PK) y enruta las consultas al shard correcto. Cada shard es una
    BD independiente.
  - Complicaciones: transacciones que cruzan shards (2PC o saga pattern),
    rebalanceo al añadir shards, resettos de schema en todos los shards.
  - Herramientas: Vitess (MySQL), Citus (PostgreSQL extension), Citus
    simplifica sharding nativo.

Sharding en NoSQL:
  - Nativo e interno al SGBD (MongoDB sharding, Cassandra con su hash de
    partición). El motor maneja la distribución de forma transparente al
    cliente.

Resumen de escalabilidad:
  Vertical (subir RAM/CPU/disco en un único nodo) -> Horizontal (añadir más
  nodos: réplicas para lectura, sharding para escritura).

----------------------------------------------------------
4. Ejemplo de clúster de alta disponibilidad en PostgreSQL
----------------------------------------------------------
Un clúster de alta disponibilidad se compone de varios servidores (nodos)
coordinados para que la BD esté siempre disponible incluso si uno falla.

Herramientas típicas en PostgreSQL:
  - Patroni: coordina la replicación automática y la conmutación por error
    (failover) sin intervención manual.
  - PgBalanceador (PgBouncer): gestiona el pool de conexiones entre la
    aplicación y los nodos del clúster.
  - ETCD o Consul: sistemas de coordinación y descubrimiento de servicios que
    Patroni usa para elegir cuál es el nodo primario.

Con Patroni + ETCD el clúster puede detectar fallos en milisegundos, promover a
un esclavo a primario automáticamente y continuar sirviendo consultas sin
interrupciones significativas.

Los clústeres de bases de datos no siempre implican múltiples servidores: en
PostgreSQL, un "cluster" también puede referirse al conjunto de bases de datos
que comparten la misma configuración y directorio de datos en un único servidor.

En resumen, los clústeres son fundamentales para garantizar rendimiento,
escalabilidad y disponibilidad, tanto en computación general como en bases de
datos.

================================================================================
MÓDULO T1: ESTÁNDARES DE NOMBRAMIENTO (NAMING CONVENTIONS)
================================================================================

Un estándar de nombramiento consistente reduce errores, facilita la revisión del
código y hace que las bases de datos nuevos se entiendan rápido entre equipos.

----------------------------------------------------------
1. Convenciones principales
----------------------------------------------------------
  - snake_case: usar minúsculas y guiones bajos para tablas, columnas, índices
    y restricciones. Ejemplo: pedido_detalle, fecha_registro.
    (Es el estándar en PostgreSQL y Rails/Django; Oracle y SQL Server suelen
    usar UPPER_CASE como predeterminado, pero snake_case se recomienda en
    nuevos proyectos.)
  - camelCase: menos común en BD; típico en Java y JavaScript. Si el equipo ya
    usa camelCase, debe mantenerse, pero es menos legible en SQL.

  - Tablas en SINGULAR: "usuario" no "usuarios". El nombre representa la
    entidad que describe la fila, no la colección. (La alternativa plural es
    válida si el equipo la elige explícitamente; lo importante es ser
    consistente.)

  - Clave primaria: se recomienda simplemente id o nombre_tabla_id.
    Ejemplo: id en usuarios, id_usuario en una tabla donde la claridad lo
    justifica.
  - Clave foránea: se recomienda el nombre de la tabla referenciada + _id.
    Ejemplo: usuario_id, producto_id.
  - Índices: ix_ + nombre_tabla + columna(s). Ejemplo: ix_pedidos_usuario_id.

  - Restricciones: prefijo según tipo - pk_, uq_, ck_, fk_.
    Ejemplo: pk_pedidos, uq_usuarios_email, fk_pedidos_usuario.

La clave del estándar no es la elección exacta sino la CONSISTENCIA en todo el
equipo y en todo el proyecto a lo largo del tiempo.


================================================================================
MÓDULO T2: SEGURIDAD Y GOBERNANZA DE DATOS
================================================================================

----------------------------------------------------------
1. Inyección de código SQL (SQL Injection) y prevención
----------------------------------------------------------
La SQL injection ocurre cuando un atacante inserta comandos SQL no deseados a
través de datos de entrada de la aplicación (formularios, parámetros de URL,
cabeceras), y el servidor los ejecuta sin sanitizar.

Ejemplo clásico de login:
  -- Si el usuario escribe en el campo:  ' OR 1=1 --
  SELECT * FROM usuarios WHERE usuario = '' OR 1=1 --' AND pass = '...';
  Esto devuelve TODOS los usuarios sin autenticar.

Prevención: CONSULTAS PREPARADAS / sentencias parametrizadas:
  -- PostgreSQL / JDBC
  PREPARE stmt AS SELECT * FROM usuarios WHERE usuario = $1 AND pass = $2;
  EXECUTE stmt('admin', 'secreto');

  -- Django (ya lo hace automáticamente)
  User.objects.filter(username=username, password=password)

Las consultas preparadas separan la estructura SQL de los datos, de modo que
los datos NUNCA se interpretan como código SQL. NUNCA concatenes datos de
usuario directamente en una cadena de consulta.

----------------------------------------------------------
2. Principio de mínimo privilegio (Gestión de usuarios y roles)
----------------------------------------------------------
  - Crear un usuario dedicado para cada aplicación (nunca usar el usuario
    superadministrador).
  - Asignar solo los permisos necesarios: SELECT, INSERT, UPDATE o DELETE sobre
    las tablas que realmente necesita.
  - Crear roles (GROUP en PostgreSQL) y asignar permisos a roles, no a usuarios
    individuales.
  - Usar GRANT y REVOKE para administrar permisos:
        CREATE ROLE app_lectura;
        GRANT SELECT ON TABLE pedidos TO app_lectura;
        CREATE USER app_backend WITH PASSWORD '...';
        GRANT app_lectura TO app_backend;

----------------------------------------------------------
3. Cifrado de datos: en tránsito (TLS/SSL) y en reposo (TDE)
----------------------------------------------------------
  - En tránsito (TLS/SSL): cifra la comunicación entre la aplicación y el
    servidor de BD para evitar escuchas pasivas y MITM. En PostgreSQL se
    configura con sslmode=verify-full en la cadena de conexión y
    ssl = on en postgresql.conf.
  - En reposo (TDE - Transparent Data Encryption): cifra los archivos en disco
    para que, si alguien roba el disco o los backups, no pueda leer los datos
    sin la clave de descifrado. SQL Server y Oracle lo soportan nativamente;
    en PostgreSQL hay extensiones (pgcrypto) o cifrado a nivel de sistema de
    archivos (LUKS, dm-crypt).

----------------------------------------------------------
4. Manejo de datos sensibles
----------------------------------------------------------
  - GDPR / protección de datos: los datos personales (nombre, email, dirección,
    IP) tienen restricciones legales de almacenamiento y uso.
  - Hashing de contraseñas: NUNCA almacenar contraseñas en texto plano. Usar
    hashing con salt (bcrypt, argon2id). Nunca md5/sha simple (son rápidos de
    rainbow table).
  - Sanitización de logs: asegurarse de que los logs no contengan datos
    sensibles como contraseñas, tokens de pago o números de seguridad social.
  - Datos de prueba: en desarrollo y staging, usar datos sintéticos anonimizados,
    nunca producción real.


================================================================================
MÓDULO T3: ESTRATEGIAS DE COPIAS DE SEGURIDAD Y RECUPERACIÓN
================================================================================

----------------------------------------------------------
1. Tipos de respaldos
----------------------------------------------------------
  - Respaldos lógicos: exportan los datos como comandos SQL o en formato
    estructurado. Herramientas:
      * pg_dump (PostgreSQL): exporta esquema + datos a un archivo .sql
      * mysqldump (MySQL/MariaDB): equivalente para MySQL.
    Ventaja: portabilidad entre versiones y SGBD distintos. Desventaja: son más
    lentos y pesados que los físicos.
  - Respaldos físicos: copian los archivos del sistema de datos ( tablespaces,
    directorios data). Son más rápidos pero menos portátiles.

----------------------------------------------------------
2. Estrategias de copia
----------------------------------------------------------
  - Backup completo: copia toda la base de datos cada vez. Simple, pero lento y
    pesado a medida que crece.
  - Backup incremental: solo copia los datos modificados desde la última copia
    (completa o incremental). Rápido, pero la recuperación requiere todas las
    copias (completa + todos los incrementales).
  - Backup diferencial: copia los datos modificados desde la última copia
    COMPLETA. La recuperación solo necesita la copia completa + la última
    diferencial. Más rápido que un completo, más pesado que un incremental.

Combinación típica: completo semanal + incremental o diario diferencial.

----------------------------------------------------------
3. Recuperación punto en el tiempo (PITR - Point-in-Time Recovery)
----------------------------------------------------------
PostgreSQL (y otros SGBD) registran TODOS los cambios en registros WAL
(Write-Ahead Logging) antes de confirmarlos en disco.

Con PITR se puede restaurar la base de datos a un momento EXACTO (por ejemplo:
"2024-12-15 14:32:00"), reproduciendo los registros WAL del backup hasta ese
punto.

Flujo:
  1. Restaurar el backup completo más reciente (base).
  2. Reproducir los WAL (archivos de registro) desde el backup hasta el momento
     deseado.
  3. La BD queda en el estado exacto de ese instante.

Parámetros clave en PostgreSQL:
  - archive_command: script que envía los WAL a almacenamiento seguro (S3,
    cinta, etc.).
  - recovery_target_time: fecha/hora objetivo de la recuperación.

PITR es la herramienta estándar para recuperarse de errores humanos (DELETE o
UPDATE accidental) sin perder datos posteriores.

MÓDULO T4: INTEGRACIÓN CON EL DESARROLLO DE SOFTWARE
================================================================================

----------------------------------------------------------
1. Gestión de migraciones de esquemas
----------------------------------------------------------
Una migración es un fichero con cambios en el esquema (CREATE TABLE, ALTER
TABLE, etc.) que se aplica de forma versionada y reproducible.

Herramientas:
  - Flyway: usa ficheros SQL versionados (V1__create.sql, V2__alter.sql) y los
    aplica en orden.
  - Liquibase: usa ficheros XML, YAML o changelogs SQL; ofrece rollback
    integrado.
  - Migraciones nativas de ORMs:
      * Django: makemigrations / migrate (genera Python que el ORM traduce a
        SQL).
      * Laravel: php artisan make:migration / php artisan migrate.
      * Alembic (SQLAlchemy/Python).

Regla clave: NUNCA editar un esquema directamente en producción sin pasar por
una migración versionada. Cada cambio se graba como fichero en el repositorio,
se revisa en code review y se aplica de forma automática.

----------------------------------------------------------
2. ORM vs SQL puro
----------------------------------------------------------
ORM (Object-Relational Mapping): capa de abstracción que mapea tablas de BD a
objetos del código fuente (clases en Python, Java, etc.).

Cuándo usar un ORM:
  - Operaciones CRUD rutinarias (creación, lectura, actualización y borrado).
  - Prototipos rápidos donde la velocidad de desarrollo es prioritaria.
  - Evitar escribir SQL repetitivo y simple.

Cuándo escribir SQL puro (raw SQL):
  - Consultas complejas con múltiples JOINs, subconsultas, window functions o
    CTEs.
  - Optimización de rendimiento crítico.
  - Migraciones de datos a gran escala.

El problema N+1: ocurre cuando el ORM, para cargar una lista de N registros,
ejecuta una consulta adicional por cada registro (N+1 consultas en total),
en lugar de una sola consulta con JOIN.

Ejemplo N+1 en Django:
  for cliente in Cliente.objects.all():
      print(cliente.pedidos.count())  -- cada vuelta hace una SELECT

Solución:
  for cliente in Cliente.objects.prefetch_related('pedidos').all():
      print(cliente.pedidos.count())  -- 2 consultas, no 1001

En general, el ORM es perfecto para la mayoría de operaciones; el SQL puro
complementa en los puntos donde se necesita control total sobre la consulta.

MÓDULO X2: CIFRADO DE ARCHIVOS CON GPG
================================================================================

Envío de un archivo de manera segura por correo electrónico (ejemplo: archivo
de base de datos exportado).

Pasos:

1. Instalar GPG (si no lo tienes):
   $ sudo apt update && sudo apt install gnupg

2. Comprimir y cifrar el archivo con una contraseña:
   $ gpg -c archivo.sql
   Esto genera archivo.sql.gpg. Se pedirá una contraseña para cifrarlo.
   Comparte la contraseña con el destinatario por un canal seguro (llamada,
   mensaje, etc.).

3. Enviar el archivo cifrado por correo electrónico.

4. Descifrar en destino:
   $ gpg -d archivo.sql.gpg > archivo.sql
   Se pedirá la contraseña que se usó para cifrar.

Nota: si se hace la prueba localmente, puede que no pida la contraseña porque
ya está en el caché de claves de GPG. Para una prueba fiable, descifrar desde
otra máquina.

Fuente: DeepSeek
